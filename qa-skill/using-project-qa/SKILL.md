# Using Project QA

Use this skill only after an explicit whole-project QA request for a supplied product target. This is the Phase 2 project route; it must not broaden, overload, or replace Phase 1 `using-qa`. Phase 1 `using-qa` remains the requirement, fix, or Diff route for single-Diff QA.

## Roles

- The main agent owns user communication, targeted clarification, target safety, human escalation, host-owned generated-validation cleanup decisions, and exact delivery.
- The Project QA Coordinator owns Project Intake, run identity, storage decision, authority checks, reachable planning, read-only execution coordination, conclusion reconciliation, and one continuously maintained project report from [`../templates/project-qa-report.md`](../templates/project-qa-report.md).
- Module QA Agents are read-only, scope-bounded, cannot delegate, and receive explicit module ID, task ID, allowed paths, risks/verification IDs, planned commands/tools, declared resources, and snapshot fingerprint before execution. They independently validate generated tests but never create or modify them.

## Required Run

1. Confirm this was an explicit whole-project QA request. If the request is only a requirement, fix, or Diff review, stop this route and use Phase 1 `using-qa` instead.
2. Record the supplied skill source path, resolved skill source path, supplied product target path, and resolved product target path as separate values. The skill source path and product target path are separate values and must never be collapsed.
3. Require an explicit product target. Do not infer the product target from the skill source path, skill location, cwd, current working directory, or ancestor repository. An absent, missing, ambiguous, unavailable, or unsafe product target stops as `BLOCKED` with an exact rerun condition.
4. Default mode is `PROJECT_QA_ONLY`; repair or fix-and-rerun orchestration cannot start without authorization. `PROJECT_FIX_AND_RERUN` requires explicit user request recorded by the Main Agent as structured user authorization: source=user, explicit=true, selected mode=`PROJECT_FIX_AND_RERUN`, non-empty request text or reference, timestamp, and record identity. Explicit recorded user authorization activates `PROJECT_FIX_AND_RERUN`; raw text, literal token presence, ordinary failure, ambiguous fix wording, wording like QA, or the presence of a target must not select, activate, infer, imply, auto-start, or start repair or `PROJECT_FIX_AND_RERUN` without that recorded authorization.
5. Create the target snapshot from the current actual project state, including uncommitted changes. Record the snapshot identity required by [`../references/project-qa-run-contract.md`](../references/project-qa-run-contract.md): `qa_session_id`, `run_id`, optional `parent_run_id`, target path, snapshot time, Git and working-tree state when available, and isolation-workspace reference tied to the source snapshot. Planning may record an unavailable workspace, but an `OPEN` gate and execution require a concrete isolated workspace reference that must not be `N/A`.
6. Decide storage using the run contract. `.qa/runs/<run_id>/` is allowed only when the path is already ignored or local-excluded and can be used without tracked-file changes. Otherwise host-owned external storage is mandatory.
7. Maintain the report shell exactly from [`../templates/project-qa-report.md`](../templates/project-qa-report.md). Through M6, fill intake, identity, storage, recovery state, bounded static capability evidence from [`../references/project-capability-discovery.md`](../references/project-capability-discovery.md), Project Inventory, Risk and Verification Plan, Project QA Plan Gate, unexecuted candidate policy records, Human Gates, missing prerequisites, host-bounded schedule records from [`../references/module-resource-scheduling.md`](../references/module-resource-scheduling.md), Module Results, Execution Evidence, generated-validation records, repair records when authorized, checkpoint/resume records, stale invalidation, conflict-stop, history comparison, authority, blocked items, Human Review Items, omissions, residual risk, conclusion, and delivery sections supported by current evidence.
8. In QA-only mode, the original/product surface remains read-only: do not modify tracked files, product source, existing tests, fixtures, snapshots, configuration, documentation, dependencies, runtime config, `.gitignore`, or create project-local `.qa/` artifacts unless the ignored/local-excluded storage rule is already satisfied without tracked-file changes. The host-only temporary generated-asset exception permits the host Main Agent or Implementation Agent to create new generated validation assets only inside the isolated workspace; successful runs must clean those assets before `PASS`; cleanup failure blocks `PASS`. Failed diagnostic retention must be explicit and host-owned. Safe tests, checks, and diagnostics run only inside that isolated workspace, never in the original target.
9. Separate Evidence authority, Report-semantic authority, Run-state authority, and Delivery authority. Any unexplained mismatch prevents `PASS`.
10. Route the same Project QA Coordinator through project-qa-plan -> project-qa-execute -> project-qa-conclude after intake, snapshot, and storage setup. Do not create a parallel planning pipeline, a second Coordinator, or a discoverable but unreachable planning, execution, or conclusion skill. Project Intake does not require a Diff.
11. Start [`project-qa-execute`](../project-qa-execute/SKILL.md) only when the Project QA Plan Gate is `OPEN`. If the gate is `BLOCKED` or has unresolved `NEEDS_HUMAN_REVIEW`, pause before execution and record the exact blocker, Human Gate, and rerun condition.
12. Route [`project-qa-repair`](../project-qa-repair/SKILL.md) only for its separated subflows: QA-only generated asset design -> host writer creates new temporary generated-validation assets -> independent execute validation -> cleanup; repair after current failure evidence plus recorded repair authorization -> host writer changes product/tests only inside isolation -> fresh execute reruns -> conclude; and M5 conflict detection/stop before any sync-like action. The host Main Agent or host Implementation Agent is the only writer inside the isolated workspace; the original target is never written, modified, synced, or back-propagated.
13. Use [`project-qa-conclude`](../project-qa-conclude/SKILL.md) to reconcile current Module Results, Execution Evidence, repair/generation validation when present, authority integrity, and exact delivery into one of the four project statuses.
14. Deliver the exact completed project report without semantic or content loss. The only project conclusions are `PASS`, `FAIL`, `BLOCKED`, and `NEEDS_HUMAN_REVIEW`; `SKIP` may describe an individual check but is not a project conclusion.

## M6 Active And Deferred Work

- Project inventory, classification, key-flow planning, risk planning, and the Project QA Plan Gate are active through `project-qa-plan`.
- Read-only project test execution, Module QA Agent execution, Module Results, Execution Evidence, resource declarations, and project reconciliation remain active.
- Temporary generated validation assets are active in M4 only inside the isolated workspace with independent read-only QA validation and cleanup before `PASS`.
- Explicit repair and fix-and-rerun are active in M4 only after explicit, recorded user authorization and only inside the isolated workspace.
- Checkpoint resume, stale invalidation, compatible history comparison, and conflict-stop are active in M5 through [`../references/project-run-recovery.md`](../references/project-run-recovery.md).
- Bounded static capability evidence and unexecuted candidate planning are active in M6 through [`../references/project-capability-discovery.md`](../references/project-capability-discovery.md). Candidate records are Planning state, not Module Results, Execution Evidence, authorization, or proof of safety.
- Host-bounded resource scheduling is active in M6 through [`../references/module-resource-scheduling.md`](../references/module-resource-scheduling.md). Scheduling records do not authorize commands.
- Successful sync and back-propagation remain forbidden; M5 conflict handling stops only and preserves original-target user bytes exactly.
- Broad or unbounded discovery, automatic dependency handling, dependency installation, downloads, network access, external-service access, credential or secret use, production or sensitive access, destructive operations, successful sync, real model runs, real project runs beyond approved safe checks, M7 docs, commits, pushes, PRs, and release approval remain deferred or forbidden.

## Stop Conditions

Stop as `BLOCKED` when the product target is absent, missing, ambiguous, unavailable, unsafe, cannot be snapshotted with current working-tree state, has a missing objective planning prerequisite, lacks a concrete isolated workspace for execution, has unavailable required runner/tool/environment/data/permission, has unsafe storage, has corrupt artifact integrity, has failed target postflight integrity, or has exact-delivery mismatch. Stop before execution when the Plan Gate is `BLOCKED` or unresolved `NEEDS_HUMAN_REVIEW`. Stop before `PASS` when authority domains mismatch, storage authority is unsafe, exact delivery cannot be proven, infrastructure integrity fails, target product files changed, or current Module Results and Execution Evidence are incomplete.
Stop as `BLOCKED` when M5 resume lineage is self, cross-session, malformed, non-immediate, or parent-as-history; when a compatible prior-history reference lacks a completed compatible prior run plus current run marked `history_comparison_ready` after current inventory/evidence are available; when checkpoint, manifest, or evidence artifacts are corrupt, truncated, missing, unsupported, hash mismatched, byte mismatched, reference mismatched, non-atomic, invalid-budgeted, invalid-no-progress, or unsafe by symlink/junction/realpath; when storage would require creating repository `.qa/`; or when conflict-stop detects added, deleted, changed, or unsafe original-target files against the complete repair-start baseline.
Stop as `BLOCKED` when M6 capability artifact paths are traversal, absolute, drive-qualified, UNC, NUL-containing, symlink, junction, realpath-escape, special files, outside the supplied target, or affected by missing/invalid roots or read/lstat/realpath races; when fallback discovery exceeds depth 8, 256 recognized artifacts, or 1048576 bytes per recognized artifact without explicit inventory paths/reduced artifacts; when recognized artifact content is malformed for a required observed capability; when an affected verification requires an unavailable already-installed local tool; when schedule task IDs are duplicate, malformed, or secret-like; when isolation keys are unsafe; when schedule resources are missing, undeclared, ambiguous, malformed, unknown-kind, non-`declared`, or secret-like; when provided isolation evidence is invalid; when a plan attempts parallel sharing without valid distinct isolation evidence; or when result/artifact paths are duplicate, canonically colliding, outside the output root, existing directory leaves, symlink/junction component paths, or otherwise unsafe. Valid declared shared mutable resources without isolation evidence are serialized and may remain schedule `ok:true`; they are not `BLOCKED` by sharing alone. Record Human Gates separately while preserving objective `BLOCKED` precedence and redacting sensitive values.
