# QA Lite

Run this skill only after [`../qa-triage/SKILL.md`](../qa-triage/SKILL.md) records `Profile Decision: LITE` in the same QA subagent session. QA-Lite is read-only and compact, but it is still evidence-first QA. It must not edit, change, modify, touch, or write product source, product target files, product tests, fixtures, snapshots, configuration, or documentation. It may write only the QA-Lite report and approved temporary QA artifacts such as evidence logs or screenshots. For the shared matrix and profile contract, see [applicability rubric](../references/applicability-rubric.md) and [QA profiles](../references/qa-profiles.md).

## Required Run

1. Create or open one Markdown report from [`../templates/qa-lite-report.md`](../templates/qa-lite-report.md). Keep the report continuously maintained.
2. Independently run Repository Preflight before actual Diff/source inspection. Confirm separate supplied and resolved skill source and product target paths, explicit product target, target-only scope, readable local target, and the existing safe local verification method. Pack self-tests are not product QA evidence.
3. Before risk planning, record compact `Change Intake`: `Observed Facts`, `Inferred Intent` with confidence and basis, `Authoritative Acceptance Criteria` with source or owner, and `Unresolved Questions`.
4. Create and keep one `qa-plan/v1` JSON Planner artifact aligned with the Lite run as an approved temporary QA artifact. The Markdown report stays authoritative and the JSON file is never product evidence. Lite uses the artifact only as a planning companion, and it must have no `Blocked` or `Deferred` matrix rows. If a row turns `Blocked` or `Deferred`, or eligibility becomes invalid, escalate to Full before execution or conclusion.
5. Build a compact 11-row canonical QA applicability matrix from [`../references/risk-checklist.md`](../references/risk-checklist.md). Lite uses the canonical QA applicability matrix to assess all 11 categories within its bounded profile or escalates to Full when it cannot justify them. Use exactly these five assessments, `Required`, `Recommended`, `Not Applicable`, `Blocked`, and `Deferred`, and keep the rationale visible for every row. Required rows need evidence before PASS. `Not Applicable` needs factual basis. `Blocked` and `Deferred` stay visible with the missing prerequisite, owner, trigger, rerun condition, and residual risk. If the bounded profile cannot justify a category assessment, escalate to Full before execution or conclusion.
6. Build a scoped Risk - Verification - Evidence chain for the bounded request. Every `Must Verify` item needs expected result, safe local method, evidence requirement, and status.
7. Before execution, when Node is already available without installation, run `node "<resolved skill source path>/tools/validate-qa-plan.mjs" "<plan.json>" --json`. The validator reads only the Planner artifact and bundled schema. A contract failure stops Lite readiness; correct a structural artifact error, or escalate to Full when the failure invalidates Lite eligibility. Validator success is planning consistency only, never product evidence. If Node is unavailable, do not install it and do not block product QA solely for that reason; disclose that deterministic validation was unavailable and manually enforce the same schema, rubric, and Lite rules.
8. Execute only existing safe local verification methods that are in scope and do not require installation, dependency mutation, generated validation, repair, recovery, production access, credentials, release action, or other Human Gate approval.
9. Record actual evidence, command/tool/request/observation, result, artifact or reference, and execution time. No evidence means no `PASS`; without evidence the item cannot PASS and overall PASS is unavailable.
10. Use exactly four statuses: `PASS`, `FAIL`, `BLOCKED`, and `NEEDS_HUMAN_REVIEW`. `PASS` requires evidence for every scoped `Must Verify`, no unresolved blocker, and no pending critical Human Gate.
11. Apply Human Gates for objective gaps, subjective owner judgment, risky resources, approvals, security/privacy/sensitive decisions, and any action outside read-only safe local verification. Keep `BLOCKED` precedence when objective prerequisites are missing.
12. After any external product repair or other material change, preserve original evidence and require fresh rerun evidence for each affected verification before changing status to `PASS`.
13. Before the QA Lite Gate and final status, update the same Planner artifact with actual statuses, evidence refs, and conclusion fields. When Node is already available without installation, run `node "<resolved skill source path>/tools/validate-qa-plan.mjs" "<plan.json>" --json --require-conclusion`. A contract failure blocks the Lite conclusion output contract. Validation success is consistency only, not product evidence. If Node is unavailable, disclose the manual fallback and enforce the same conclusion rules without installing it.
14. Deliver the complete authoritative report by exact relay. When the host provides completed child result authority, use that exact relay as the authoritative report; preserve `child-report-relay-evidence` or `report-source` style metadata when available. Do not reconstruct a summary in place of the report.

## Escalation While Running

If any fact invalidates Lite eligibility, stop Lite execution, record `Profile Decision: FULL`, list the invalidating fact, and expand the same authoritative report to [`../templates/qa-report.md`](../templates/qa-report.md), preserving all triage, preflight, intake, evidence, findings, and unresolved items already recorded. Then continue the same QA subagent through the unchanged Full route in [`../qa-plan/SKILL.md`](../qa-plan/SKILL.md), [`../qa-execute/SKILL.md`](../qa-execute/SKILL.md), and [`../qa-conclude/SKILL.md`](../qa-conclude/SKILL.md). Do not create a parallel report or discard earlier evidence. Cross-module architecture risk, ambiguous acceptance or root cause, security or privacy scope, data migration, permissions, release, operational risk, uncertainty affecting `Must Verify`, generated validation, repair, recovery, history, capability discovery, resource scheduling, explicit full, whole-project, project-wide, audit, or release QA all escalate to Full. If the bounded profile cannot justify any category assessment in the canonical applicability matrix, or cannot support a row with factual evidence or a clear rerun condition, escalate to Full before execution or conclusion. The Planner artifact must have no `Blocked` or `Deferred` rows while the route remains Lite.

## Non-goals

- No product mutation, automatic product repair, generated checks, generated validation, test maintenance, recovery/resume handling, capability discovery, resource scheduling, project-mode Lite, release approval, commit, push, PR, or multi-agent flow.
- No project-wide claim. QA-Lite can conclude only on the scoped bounded target and evidence in its report.

For routing details, read [`../references/qa-lite-triage.md`](../references/qa-lite-triage.md). For shared Human Gate semantics, read [`../references/human-gates.md`](../references/human-gates.md).
