# QA Skill MVP 需求说明

> 状态：Draft v0.1
> 日期：2026-07-21
> 适用范围：QA Skill MVP

## 1. 文档定位

本文档用于固定 QA Skill MVP 的产品范围、核心流程、交付形式和验收标准。

如本文档与以下早期调研文档存在冲突，以本文档为准：

- `github项目调研报告.md`
- `qa-workflow-skill-research-and-dev-plan.md`

早期调研仍作为方案来源，但其中“默认以 Web/Playwright 为核心”以及“MVP 不指导真实执行”等假设，不再作为当前 MVP 约束。

## 2. 北极星定位

**帮助 QA 流程不成熟的团队，完成可信、可追溯、基于证据的 QA。**

QA Skill 不替代人工 QA，也不替代最终发布决策。它提供一套稳定、可复用的 QA 工作方法，确保团队能够：

- 明确本次需要验证的目标。
- 根据风险决定验证范围和优先级。
- 使用项目现有能力完成可执行的验证。
- 为通过、失败和阻塞结论保留实际证据。
- 明确暴露未验证内容、人工判断项和剩余风险。

## 3. MVP 目标

MVP 用于验证以下核心假设：

> 现有 Agent 加载一套结构化 QA Skill 后，能够围绕一次需求或变更，稳定完成从目标理解到 QA 结论的完整流程，并产出一份可供人工复核的 QA 报告。

MVP 的成功不以“全自动 QA”为标准，也不要求接入 CI/CD。

## 4. 目标用户与触发场景

### 4.1 目标用户

- 尚未建立统一 QA 流程的研发团队。
- 需要对功能或代码变更进行系统验证的开发、产品或项目负责人。
- 需要了解已验证内容、缺陷、阻塞项和剩余风险的交付人员。

目标用户不被定义为“没有 QA 经验的人”。

### 4.2 MVP 触发场景

一次功能、修复或代码变更已具备可验证条件时，用户手动要求现有主 Agent 执行 QA。

MVP 以“一次需求或一次变更”为基本 QA 单位，不处理完整发布批次的聚合管理。

## 5. 交付形式

MVP 交付为一个参考 Superpowers 组织方式的 **QA Skill Pack**，由现有主 Agent 手动加载。

最小结构如下：

```text
qa-skill/
├── using-qa/
│   └── SKILL.md
├── qa-plan/
│   └── SKILL.md
├── qa-execute/
│   └── SKILL.md
├── qa-conclude/
│   └── SKILL.md
├── references/
│   ├── qa-principles.md
│   ├── risk-checklist.md
│   ├── evidence-guide.md
│   ├── finding-classification.md
│   └── human-gates.md
└── templates/
    └── qa-report.md
```

各部分职责：

- `using-qa`：定义使用时机、总体流程、角色边界和禁止事项。
- `qa-plan`：理解目标、分析风险并设计验证方案。
- `qa-execute`：执行验证、收集证据并记录发现。
- `qa-conclude`：分类问题、检查未验证项并形成最终报告。
- `references`：保存稳定的 QA 方法、定义和检查清单。
- `templates`：提供统一的 QA 报告结构。

MVP 不使用全局 Session Hook，不要求每次开发活动都自动进入 QA 流程。

## 6. 角色与责任

### 6.1 主 Agent

主 Agent 负责：

- 加载并遵循 QA Skill Pack。
- 收集用户提供的需求、变更和项目上下文。
- 控制本次 QA 的范围。
- 启动并持续复用一个 QA Subagent 会话。
- 将 QA Subagent 的澄清问题和人工门禁请求转交给用户。
- 向用户交付最终 QA 报告。
- 确保最终接受、继续处理或发布决策由人类作出。

### 6.2 QA Subagent

QA Skill 指导主 Agent 调用一个通用 Subagent，并通过固定提示明确其 QA 角色。

QA Subagent 负责：

- 独立理解目标并挑战未经验证的假设。
- 识别风险并设计相关验证项。
- 使用当前项目已有的工具和检查能力执行验证。
- 收集并引用实际证据。
- 分类问题、阻塞项和人工判断项。
- 在一次 QA 运行中持续维护同一份 QA 报告。

QA Subagent 不得：

- 修改产品源代码或产品测试代码。
- 自动修复发现的问题。
- 将自身运行成功等同于 QA 通过。
- 自行扩大 QA 范围。
- 做最终发布决定。

### 6.3 人类

以下事项必须保留人工判断：

- 需求或验收标准存在关键歧义。
- 主观 UX、视觉、产品体验或业务意图判断。
- 高风险、破坏性或不可逆操作。
- 凭证、敏感数据和外部环境的使用。
- QA 范围扩大。
- 最终接受或发布决定。

## 7. 输入要求

一次 QA 运行应尽量获得以下输入：

- 需求、Issue、变更说明或预期行为。
- 可用的验收标准和明确非目标。
- 代码 Diff、受影响范围及相关完整上下文。
- 项目已有的测试、构建命令和验证工具。
- 可用环境、测试数据、账号和权限限制。
- 已知风险、历史问题或本次特殊约束。

如果缺少的信息会影响目标理解、风险判断或验证设计，主 Agent 必须提出针对性问题。

允许继续使用非关键假设时，必须在报告中记录假设内容、依据和可能影响。关键上下文缺失时不得猜测并给出 PASS。

## 8. 核心 QA 流程

MVP 必须保持以下顺序：

```text
理解目标
  → 分析风险
  → 设计验证
  → 执行并收集证据
  → 分类问题
  → 形成结论
```

### 8.1 理解目标

明确：

- 本次 QA 要回答什么问题。
- 需求或变更期望产生什么行为。
- 什么结果代表成功。
- 哪些内容不在本次范围内。
- 哪些信息仍不确定。

### 8.2 分析风险

根据项目和变更识别相关风险，包括但不限于：

- 核心功能错误。
- 相邻功能回归。
- 数据、状态和边界条件。
- 权限、安全和隐私。
- 外部依赖与环境。
- 性能、可靠性和兼容性。
- UX、视觉和人工体验。

风险必须被划分为必须验证、应该验证、可选验证或明确不验证，并说明理由。

### 8.3 设计验证

每个关键风险必须对应至少一个验证项，或明确说明无法验证的原因。

验证项至少包含：

- 验证目标。
- 前置条件。
- 验证方法或步骤。
- 预期结果。
- 所需证据。
- 是否需要人工判断。

验证方式由项目风险和现有能力决定，可以是单元、API、集成、性能、E2E、安全、兼容性或人工检查。MVP 不默认 Web，也不默认 Playwright。

### 8.4 执行并收集证据

QA Subagent 使用宿主运行时当前可用的工具和项目已有命令完成验证。

证据可以包括：

- 命令输出和测试报告。
- 请求与响应。
- 日志和运行记录。
- 截图、录屏或界面状态。
- 性能或安全工具结果。
- 人工检查记录。

“计划执行”“看起来正常”“已有测试”均不构成实际通过证据。

### 8.5 分类问题

发现的问题至少应区分为：

- 产品缺陷。
- 测试或验证问题。
- 环境、数据、权限或依赖问题。
- 需求或验收标准问题。
- 需要人工判断的问题。
- 暂时无法确认的问题。

每个问题必须记录实际观察、预期行为、证据引用、影响和建议下一步。

### 8.6 形成结论

结论必须说明：

- 已验证并通过的内容。
- 已确认的失败和缺陷。
- 被阻塞或未验证的内容。
- 仍需人工判断的内容。
- 剩余风险。
- 本次 QA 的总体状态。

## 9. 阶段门禁

### 9.1 计划门

在目标、风险和验证计划明确前，不得开始执行验证。

### 9.2 证据门

没有实际证据的验证项不得被标记为 PASS。

### 9.3 结论门

在所有发现、未验证项和阻塞项完成分类前，不得形成总体结论。

### 9.4 人工门

涉及歧义、主观体验、敏感资源、高风险操作或最终发布判断时，必须等待人工决定。

## 10. 输出要求

一次 QA 运行的主要产物是一份从计划阶段开始持续更新的 Markdown QA 报告。

报告至少包含：

```markdown
# QA Report

## Objective and Scope
## Inputs and Assumptions
## Risk Analysis
## Verification Plan
## Execution and Evidence
## Findings
## Unverified and Blocked Items
## Human Review Items
## Residual Risks
## Overall Status and Conclusion
```

报告中的总体结论必须能够追溯到风险、验证项、执行结果和证据。

## 11. 状态定义

### PASS

仅当所有必须验证项都有实际证据、没有未解决的阻塞风险、也没有关键人工判断待处理时，才能标记为 PASS。

PASS 表示本次约定范围内的 QA 条件满足，不代表系统不存在任何问题，也不代表自动批准发布。

### FAIL

存在证据证明关键预期未满足，或存在尚未解决的阻塞缺陷。

### BLOCKED

由于关键上下文、环境、数据、权限、依赖或工具不可用，必须验证项无法完成。

BLOCKED 不等于 FAIL，也不等于 PASS。

### NEEDS_HUMAN_REVIEW

已有信息或证据不足以替代产品、业务、设计或其他人工判断。

NEEDS_HUMAN_REVIEW 不得被解释为 PASS。

## 12. MVP 功能需求

- **FR-01 手动入口**：用户可以明确要求主 Agent 启动一次 QA 运行。
- **FR-02 上下文检查**：关键输入不足时，主 Agent 提出针对性问题或明确阻塞。
- **FR-03 QA 计划**：在执行前生成目标、范围、风险和验证计划。
- **FR-04 风险驱动**：根据项目风险选择验证方式，不执行固定的通用测试套餐。
- **FR-05 技术中立**：不默认 Web、Playwright 或其他特定技术。
- **FR-06 Subagent 隔离**：使用一个动态 QA Subagent 承担独立 QA 工作。
- **FR-07 真实执行**：可以指导或运行项目当前已有的确定性检查。
- **FR-08 证据引用**：关键 PASS 或 FAIL 结果必须关联实际证据。
- **FR-09 持续报告**：同一 QA 运行持续维护一份 Markdown 报告。
- **FR-10 显式未知**：所有未执行、受阻或证据不足的事项必须单独列出。
- **FR-11 人工判断**：需要人工判断的事项必须触发人工门。
- **FR-12 源码保护**：QA Subagent 不得修改产品代码或测试代码。
- **FR-13 状态准确**：Subagent 运行成功不得被当作 QA PASS。

## 13. MVP 明确不做

- CI/CD 集成和自动调度。
- 永久配置的专用 QA Agent。
- 多 Subagent QA 流水线。
- 自动发布门禁或自动发布决策。
- 自动生成、修改或修复产品测试。
- 自动修改产品代码。
- 自愈和自动放宽断言。
- 新建测试基础设施或测试平台。
- Dashboard 和长期质量数据平台。
- 完整的领域适配器框架。
- 默认 Web 或 Playwright 优先。
- 自动积累、学习或推断项目规则。
- 代替人工完成主观体验和最终审批。

## 14. 延后功能

以下内容来自项目立项讨论，但属于后续功能候选，不改变北极星定位和核心 QA 流程：

- 保存人工确认过的项目 QA 规则。
- 后续变更复用已有验收规则。
- 比较 Agent 报告与人工体验结果。
- 将新发现整理为待人工批准的规则建议。
- 跨运行、跨项目的 QA 经验复用。
- CI/CD、定时运行和发布门禁。

## 15. MVP 验收标准

MVP 交付必须满足：

1. 包含 `using-qa`、`qa-plan`、`qa-execute`、`qa-conclude`、references 和 QA 报告模板。
2. 能以非 Web 项目为例完成 QA，不强制使用 Playwright。
3. 能围绕一次需求或变更建立目标、风险和验证计划。
4. 在计划完成前不会直接执行或声称验证通过。
5. 主 Agent 能调用一个角色明确的 QA Subagent，并保留人工沟通职责。
6. QA Subagent 不修改产品源代码或测试代码。
7. 能使用项目已有命令或工具执行至少一种真实验证。
8. 每个关键 PASS 或 FAIL 结果都有可复查的证据引用。
9. 无证据、未执行或无法执行的内容不会被标记为 PASS。
10. 报告明确区分 PASS、FAIL、BLOCKED 和 NEEDS_HUMAN_REVIEW。
11. 报告包含目标、范围、风险、验证计划、执行证据、问题、未验证项、人工判断项和剩余风险。
12. 总体结论能够追溯到对应的风险、验证项和证据。
13. 歧义需求、主观体验、高风险操作和最终发布决定均保留人工门。
14. 交付内容不包含本文件“明确不做”中的扩展能力。

## 16. MVP 完成定义

使用一个真实项目中的单次需求或变更运行 QA Skill Pack，现有主 Agent 能够：

1. 完成必要的上下文澄清。
2. 启动并复用一个 QA Subagent 会话。
3. 按核心 QA 流程完成计划、执行和结论。
4. 使用现有项目能力完成真实验证。
5. 生成一份证据充分、未知项明确、可供人工复核的 Markdown QA 报告。

满足以上条件，即认为 MVP 已验证 QA Skill 的核心产品假设。
