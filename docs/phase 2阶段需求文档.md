## 2. 产品定位

### 2.1 核心定位

Phase 1 已经在一次需求、修复或代码 Diff 上建立了以证据为基础的 QA 方法。Phase 2 将同一套方法应用到**整个当前项目**，以项目当前实际代码状态为验证对象，形成可复查的项目级风险、模块覆盖、执行证据和剩余风险报告。

Phase 2 的产品定义不是跨 Diff 报告聚合。历史 QA 报告不是启动项目 QA 的必需输入；如果存在同一项目可用的上一次运行，系统应自动比较新出现、已修复或持续存在的问题。当前状态始终由本次运行的实际执行证据决定。

QA Skill 仍然不是测试框架、测试平台、自动发布系统或替代人工判断的自治系统。它提供项目盘点、风险驱动的验证编排、必要的测试生成与修复协作、证据保留和人工决策支持。

### 2.2 目标用户体验

产品面向不具备专业 QA 方法的用户提供低摩擦入口。用户可以用自然语言提出“QA 整个项目”，不需要了解模块划分、测试层级或 Agent 内部协议。系统应自动完成以下工作：

1. 盘点项目、模块、服务、入口、依赖、已有测试和可用工具。
2. 识别重要模块、关键流程、共享依赖和高风险边界。
3. 生成项目级 QA 计划，说明范围、非目标、风险、验证方法和 Human Gate。
4. 完成计划并打开计划门；只有真正需要用户决定的事项才暂停。
5. 按项目阶段提供简单进度，例如“盘点中”“计划完成”“验证中”“修复重跑中”“报告整理中”。不向用户默认展示详细的技术流式事件。
6. 交付简明摘要和完整权威项目 QA 报告，明确已验证内容、失败、阻塞、人工判断、清理结果和剩余风险。

用户不应因为缺少 QA 经验而被要求手动选择每一个测试层。系统仍不得替用户猜测关键业务预期，也不得把用户未作答视为高风险操作的批准。

### 2.3 真实项目效果验证原则

Phase 2 的产品价值是 QA Skill 的项目理解、风险选择、测试决策、执行证据和结论质量。效果验证不依赖新的策略引擎、生产运行时或语言适配器作为产品交付物。Skill 保持技术中立，使用宿主和项目已有的工具完成验证；不要求安装新的测试运行时，不要求为每种语言编写适配器。

效果通过配对基准实验衡量：对同一份冻结的项目快照、同一请求、同一模型、同一 Agent 和同一预算，分别运行两组实验。

- **Baseline 组**：不加载 Phase 2 Skill pack，使用宿主默认 Agent 能力完成项目 QA。
- **Skill 组**：加载当前版本 Phase 2 Skill pack，使用相同的宿主和项目工具完成项目 QA。

两组实验的产出按以下维度比较，形成 Skill 效果证据：

1. **客观结论正确性**：项目级 `PASS` / `FAIL` / `BLOCKED` / `NEEDS_HUMAN_REVIEW` 判定是否与项目客观状态一致。判定依据为项目实际代码、测试和已知问题，不依赖模型自评。
2. **风险与重要模块 / 关键流程覆盖**：是否识别出项目的重要模块、关键流程和高风险项，覆盖是否充分，遗漏是否有合理说明。
3. **命令相关性与实际执行证据**：执行的命令是否与项目验证目标相关，是否产出可复查的实际执行证据（命令原文、退出码、观察结果、产物引用），是否存在无意义或重复命令。
4. **可追溯性**：每个 `Must Verify` 项是否形成 `Risk → Verification → Evidence → Status` 追踪链，证据是否可独立复查。
5. **BLOCKED 与 Human Gate 处理**：缺少前提时是否正确标记 `BLOCKED` 并记录重跑条件；需要人工判断时是否正确进入 Human Gate，不静默跳过或伪造状态。
6. **只读合规**：是否保持对项目文件的只读访问，不修改产品代码、测试、配置或文档（`.qa/` 运行产物区域除外）。
7. **报告完整性**：是否产出包含范围、计划、执行证据、模块结果、发现、未验证项、Human Gates、剩余风险和结论门的完整报告。
8. **成本 / 时间透明度**：是否记录运行时间、模型调用次数或 token 消耗等可比较的成本指标。

**实验材料要求**：优先使用真实公开仓库的已知 issue 修复前 / 修复后配对快照。修复前快照包含客观可复现的缺陷或测试失败，修复后快照中该缺陷已被修正。配对快照使两组实验的预期结论客观可验证：修复前应判定为 `FAIL`，修复后应判定为 `PASS`。

如果真实 issue 配对不可得，可以使用人工注入故障的变体作为降级方案。注入故障的实验必须显式标注为 fallback，不能用于支持"真实项目效果"声明，仅可用于验证 Skill 的检测能力是否退化。

**安全边界**：以下 M1-M7 安全约束在基准实验中与生产使用中同等生效，不因实验场景放宽：

- 不自动安装依赖、运行时、工具链或系统包。
- 不发起网络出站连接（包括包注册表、外部 API 和远程资源）。
- 不使用凭证、token、密钥或认证信息。
- 不访问生产环境、生产数据或真实外部系统。
- 不向原始项目目录写入受跟踪文件。
- 不自动 Git commit、push 或创建 PR。
- 不自动批准发布。

这些约束是 Skill 和宿主的通用安全边界，不作为独立策略引擎或运行时的产品功能对外交付。

## 3. 范围、对象与模式

### 3.1 默认验证对象

默认目标是用户明确选定的项目目录的**实际当前代码状态**，包括未提交变更。系统必须记录本次运行的快照身份，至少包括目标路径、快照时间、可识别的提交信息、工作树状态、运行 ID 和隔离工作区标识。不能因为 Skill 目录、当前工作目录或方便探测到的祖先仓库而推断项目目标。

项目可以是单体仓库、单服务仓库、Monorepo 或包含多个服务的目录。Monorepo 和多服务项目仍被视为一个项目，由不同模块工作者执行分工，并额外验证跨服务 API、数据流和用户流程。

### 3.2 用户模式

#### 3.2.1 `PROJECT_QA_ONLY`

这是默认模式，由“QA 整个项目”“帮我检查整个项目”等请求触发。

- 当前项目的产品源代码、产品测试、配置、文档、fixtures 和 snapshots 保持不变。
- `.qa/` 是唯一允许写入当前项目目录的 QA 运行产物区域，不属于产品修改面。该目录必须已被 Git 忽略，或由宿主使用不修改受跟踪文件的本地排除机制处理；如果无法安全隔离，则运行产物必须写入宿主持有的项目外存储，并在报告中保存引用。
- 系统可以在隔离副本中生成并运行临时测试、脚本或测试数据。
- 临时测试、临时数据、日志和其他运行产物在运行结束后清理，除非报告明确说明因失败诊断而按保留策略保存。
- 除获准的 `.qa/` 运行产物区域外，系统不得修改当前项目的产品代码、产品测试、配置、文档、fixtures 或 snapshots。
- 发现问题时提供证据、影响、建议和可选的建议补丁，但不把建议补丁同步回当前项目。
- 不得自动提交、推送或批准发布。

#### 3.2.2 `PROJECT_FIX_AND_RERUN`

该模式必须由用户明确请求，例如“修复问题并重新跑完整项目 QA”。没有明确请求时不得进入该模式。

- 在隔离副本中生成缺失测试，修复产品代码或验证资产，并执行受影响测试及项目回归。
- 只有验证完成且证据满足同步条件时，才把已验证变更同步回当前项目。
- 同步回当前项目后仍不自动提交 Git，不推送，不做发布批准。
- 原始失败、根因假设、每轮修改和每轮 fresh rerun evidence 必须保留。
- 不得通过删除测试、跳过检查、放宽有效断言或掩盖失败来制造 `PASS`。

### 3.3 非目标

Phase 2 不包含以下承诺：

- 不把跨 Diff 聚合定义为产品核心。
- 不提供自动发布批准、上线决定或 go/no-go 结论。
- 不默认修改产品，不默认安装依赖，不默认访问外部服务。
- 不实现 Phase 3 的 Issue、PR、Jira 或其他外部项目记录发现。
- 不实现 Phase 4 的项目知识持久化或未经批准的自动学习。
- 不宣称穷尽覆盖、全部缺陷发现、质量认证或所有项目的普适可靠性。
- 不承诺所有 OpenCode 版本、宿主或执行环境的通用兼容性。
- 不自动 Git commit、push 或创建 PR。
- 不把模型上下文摘要、提示、事件或 Agent 自述当作证据。

## 4. 角色与 Agent 架构

### 4.1 Main Agent

Main Agent 负责用户沟通、模式选择、明确目标和约束、转交 Human Gate、隔离工作区同步和最终交付。文件写入只能由 Main Agent 或独立实施 Agent 在明确进入 `PROJECT_FIX_AND_RERUN` 后、作为 QA 执行边界之外的实施动作完成。Main Agent 不自动提交，不把自己的摘要当作 QA 证据，不改写完整权威报告。

### 4.2 Project QA Coordinator

Project QA Coordinator 负责：

- 项目预检、快照身份和项目清单。
- 模块、服务、关键流程和共享依赖识别。
- 风险与覆盖计划、模块分区和验证层选择。
- 计划门和结论门的协调。
- 汇总模块证据、发现、未验证项、阻塞项和人工判断。
- 依据当前执行证据生成最终项目 QA 报告。

Coordinator 不得以模块数量、通过数量或覆盖率代替风险判断。

### 4.3 Multiple Module QA Agents

Multiple Module QA Agents 在明确的模块范围内执行只读验证并捕获证据。互不共享可变环境的模块可以并行运行；共享数据库、端口、文件、外部服务或测试数据的模块必须顺序运行，或使用明确隔离的资源。

模块 Agent 不得扩大范围，不得修改项目文件，不得独立改变项目总体状态，不得用模块摘要替代执行证据。每个模块结果必须能追溯到模块、验证项、命令或工具、观察结果、退出码、产物和状态。

### 4.4 Host-owned run registry

运行注册表由宿主持有，位于模型上下文之外，是运行状态、检查点、模块结果索引和产物引用的规范来源。它不替代完整 Markdown 报告的语义 authority，也不替代实际命令、工具和产物证据。模型上下文摘要只能帮助恢复工作，不能成为权威状态或证据。

QA Coordinator 和 Module QA Agents 始终保持只读，不直接修改产品或测试文件。测试生成、产品修复和变更同步由宿主编排的 Main Agent 或实施 Agent 完成，再由独立 QA Agents 使用 fresh evidence 验证。

## 5. 项目级 QA 工作流

### 5.1 共同流程

1. Main Agent 接收自然语言请求，确认显式项目目录、模式、范围、非目标和已知约束。
2. Coordinator 执行 Project Preflight，识别项目边界、快照身份、提交和工作树状态、技术栈、模块、入口、已有测试、可用工具及危险操作。
3. 系统将当前项目复制或快照到临时隔离工作区。后续测试和修复只在隔离工作区中进行。
4. Coordinator 形成项目级 `Project Intake` 和项目清单，分开记录 `Observed Facts`、`Inferred Intent`、`Authoritative Acceptance Criteria` 和 `Unresolved Questions`。`Project Intake` 不要求存在 Diff。
5. Coordinator 识别重要模块和关键流程，建立风险、模块、验证和证据计划。
6. 系统对安全、性能、兼容性和可访问性等专项测试进行风险选择，不机械地对每个项目执行每一层。
7. 完成 `QA Plan Gate`。关键验收标准、敏感资源、高风险操作或范围冲突未解决时，暂停并进入相应 Human Gate 或 `BLOCKED`。
8. 安全的本地既有测试按项目实际能力尽可能完整执行，并记录命令、范围、退出码和产物。
9. Coordinator 将模块工作分配给 Module QA Agents。独立模块可并行，共享资源模块按计划顺序执行。
10. 按模式执行临时测试生成、测试验证、产品修复和 fresh rerun。
11. Coordinator 汇总所有模块结果，核对关键流程是否有当前执行证据，保留低风险遗漏和专项省略理由。
12. 完成 `QA Conclusion Gate`，计算项目状态并生成完整权威项目 QA 报告。
13. `PROJECT_QA_ONLY` 清理临时产物。`PROJECT_FIX_AND_RERUN` 先完成冲突检查和验证，再仅同步已验证变更。
14. Main Agent 向用户交付简明摘要、完整报告引用、变更和测试保留或清理说明、Human Gates 与剩余风险。

### 5.2 安全检查与批准

安全的本地现有测试应尽可能完整执行。以下操作不能默认执行，必须在计划中列为 Human Gate，并取得用户批准：

- 长时间运行、付费、外部服务或网络调用。
- 需要凭证、权限、个人数据、敏感数据或生产数据。
- 依赖安装、升级或下载。
- 生产环境、真实支付、真实外部系统或不可回滚环境操作。
- 数据库迁移、权限变更、安全策略变更或破坏性操作。

缺少需求时，系统先验证能够从当前项目和明确验收标准确定的行为。只有关键业务行为确实存在歧义时才提问，不为低风险细节制造额外问答。

### 5.3 重要模块、关键流程和 Must Verify 分类规则

Coordinator 必须为模块、流程和风险记录分类结论、依据和来源。不能只输出“重要”或“高风险”而不说明原因。

模块满足以下任一条件时，默认属于重要模块：

- 承担项目主要目的、主要用户入口或核心业务能力。
- 处理身份认证、权限、支付、资金、隐私、敏感数据或持久化数据。
- 是多个模块共同依赖的基础组件、公共接口、数据模型、配置或运行入口。
- 失败会导致项目无法启动、构建、部署、执行主要流程或恢复数据。
- 被用户、项目文档、验收标准或运行配置明确标记为关键。

关键流程是完成项目主要目的所必需的端到端路径，或跨越重要模块、服务、接口和数据边界的主要操作。Monorepo 和多服务项目至少要覆盖主要入口到关键结果的跨服务流程。

风险满足以下任一条件时，默认标记为 `Must Verify`：

- 可能导致核心功能不可用、数据错误、权限绕过、安全问题、资金错误或不可恢复影响。
- 直接影响重要模块或关键流程。
- 缺少证据会使项目总体状态无法可靠判断。
- 属于用户、验收标准、法规、安全规则或项目运行要求明确规定的必测内容。

低风险模块或验证项只有在影响有限、依赖关系清楚、未触及关键流程且省略理由可复查时，才能标记为 `Should Verify`、`Optional` 或 `Explicitly Not Verified`。如果业务重要性无法从项目和权威标准中判断，必须进入 Human Gate；不得通过自行降低优先级来获得 `PASS`。

## 6. 测试生成与自动修复

### 6.1 自动生成测试生命周期

1. Coordinator 依据风险和关键流程设计测试用例、预期结果和证据要求。
2. Main Agent 或实施 Agent 在隔离工作区中负责写入测试文件、fixtures 或临时脚本。
3. QA Agents 独立检查生成测试是否覆盖指定风险，断言是否有明确依据，是否存在循环自证、过宽匹配、永久跳过或不可靠 oracle。
4. 在 `PROJECT_QA_ONLY` 中，生成测试只作为临时验证资产，运行后清理。
5. 在 `PROJECT_FIX_AND_RERUN` 中，只有稳定、与需求一致、经独立验证且对回归有长期价值的测试才可保留并同步。
6. 临时脚本、临时数据、日志、截图和视频按清理策略处理。无效或 flaky 测试不得被保留为成功证据。

系统绝不能删除已有测试、跳过检查或弱化有效断言以获得 `PASS`。测试问题与产品问题必须分开分类，并重新验证受影响范围。

### 6.2 自动修复生命周期

**修复在真实项目上保持禁用状态，直到 QA-only 配对基准门全部通过。** 在基准门通过之前，自动修复仅可在 fixture 和受控测试环境中验证其生命周期正确性，不得在任何真实项目上执行修复或同步操作。

自动修复仅在 `PROJECT_FIX_AND_RERUN` 中可用，并遵循以下顺序：

1. 保留原始失败命令、输出摘要、退出码、环境和 Evidence ID。
2. 记录根因假设、依据、影响范围和最小修改计划。
3. 在隔离工作区应用最小 Diff。
4. 先重新执行原始失败测试，确认修复目标。
5. 再执行受影响模块测试和项目回归。
6. 使用 fresh rerun evidence 更新结果，但不覆盖原始失败。
7. 每次运行最多进行 3 轮修复。第 3 轮后仍失败时停止修复并报告，不继续循环。

数据库 schema、权限、安全、支付、敏感数据、生产数据或破坏性操作相关改动必须取得批准。修复不得绕过 Human Gate，也不得自动扩大到无关模块。

## 7. 隔离、同步与冲突

### 7.1 隔离原则

系统必须将当前项目复制或快照到临时隔离工作区。测试生成、测试执行、产品修复、诊断和清理均在隔离工作区进行。隔离工作区必须能识别来源快照，并记录与当前项目的对应关系。

### 7.2 同步条件

在完成全部计划验证、受影响测试和项目回归后，系统才能在 `PROJECT_FIX_AND_RERUN` 中同步变更。只同步已验证、来源明确且属于本次运行的变更。同步前必须检查当前项目是否仍与开始时的快照一致。

### 7.3 冲突处理

如果原始项目在运行期间发生变化，系统必须停止同步并报告冲突。系统不得覆盖用户的新变更，不得通过自动合并掩盖冲突，不得在冲突状态下宣称同步成功。用户处理冲突后，可以从检查点恢复，并重新验证受影响工作。

## 8. 状态、证据与历史比较

### 8.1 项目 PASS 规则

项目只有在以下条件同时满足时才能为 `PASS`：

- 每个重要模块和关键流程都有当前运行的实际执行证据。
- 所有 `Must Verify` 风险均有 `Risk → Verification → Evidence → Status` 追踪链。
- 关键预期已满足，没有未解决的关键阻塞或关键 Human Gate。
- 生成测试和修复测试已经过独立 QA 验证。
- 未验证的低风险项、专项省略和剩余风险仍在报告中可见。

`PASS` 仅表示本次项目范围和当前快照的 QA 条件满足，不表示整个产品没有缺陷、已经穷尽覆盖或已获得发布批准。

### 8.2 四种状态

| 状态 | 项目级含义 | 不能解释为 |
|---|---|---|
| `PASS` | 重要模块和关键流程有当前执行证据，必须验证项满足，未解决的关键阻塞和关键人工判断不存在。 | 全部正确、穷尽验证或发布批准。 |
| `FAIL` | 当前执行证据证明关键预期未满足，或已确认的产品缺陷仍存在。 | 环境缺失、权限缺失或未执行的替代标签。 |
| `BLOCKED` | 关键验收前提、环境、数据、权限、工具或冲突使必须验证项无法可靠完成。 | 产品缺陷或通过。 |
| `NEEDS_HUMAN_REVIEW` | 有客观执行证据，但业务、体验、设计、安全、隐私、可访问性或责任人判断仍不可由系统替代。 | 通过、拒绝发布或自动批准。 |

当缺少或矛盾的客观验收前提阻止定义预期或执行 `Must Verify` 时，`BLOCKED` 优先于 `NEEDS_HUMAN_REVIEW`。所有状态都必须能回到当前证据，不能由历史报告或模型摘要单独产生。

### 8.3 历史比较

如果存在同一项目可用的上一次运行，系统应自动比较并识别：

- 新出现的问题。
- 本次已修复的问题。
- 持续存在的问题。
- 已不再适用或被撤销的历史问题。

历史报告和运行清单长期保留，作为比较上下文和审计来源。当前运行的实际执行证据始终决定当前状态。大型日志、截图和视频按可配置的保留策略清理，清理不得删除报告中的必要摘要、Evidence ID、哈希或重跑条件。

## 9. 持久化、断点恢复与权威报告

### 9.1 Authority 分工与冲突规则

Phase 2 不使用单一文件替代所有类型的 authority，而是按职责区分：

| Authority 类型 | 权威来源 | 作用 |
|---|---|---|
| 执行证据 authority | 实际命令、工具结果、退出码、产物和经过脱敏的观察记录 | 证明测试实际发生及观察到的行为。 |
| 报告语义 authority | 完成结论门后的完整 Markdown 项目 QA 报告 | 表达本次项目范围、风险、验证、发现、状态和剩余风险。 |
| 运行状态 authority | 宿主持有的 run registry 和 manifest | 记录阶段、检查点、模块索引、产物引用、哈希、清理和同步状态。 |
| 交付 authority | 宿主取得的已完成 Project QA Coordinator 结果 payload | 向用户精确交付完整 Markdown 报告，不依赖 Main Agent 重构。 |

run manifest 必须记录完整报告及关键产物的哈希和引用。报告内容、manifest、模块结果或实际证据发生无法解释的不一致时，结论门不得完成，运行必须标记为基础设施或报告一致性失败，不能输出 `PASS`。run registry 不能用状态字段覆盖报告语义，报告也不能改写实际命令和产物证据。

交付继续遵守 Phase 1 的 exact delivery 合同：宿主直接交付有效的已完成结果 payload；提取后执行 byte/string exact comparison；raw parent final message 只保留为诊断证据；引用的报告 artifact 只能作为 mirror，并且必须与交付 authority 一致。

### 9.2 运行目录

每次运行优先在项目目录下的 `.qa/runs/<run-id>/` 持久化运行信息，但 `.qa/` 必须是已批准且被 Git 忽略的 QA 产物区域。宿主不得为了建立该目录而修改受跟踪的 `.gitignore` 或其他产品文件；可以使用已有忽略规则或本地非受跟踪排除机制。如果不能安全建立项目内产物区域，则必须使用宿主持有的项目外运行目录，并在最终摘要中提供引用。

运行目录至少包括：

- 完整且权威的 Markdown 项目 QA 报告。
- run manifest，包括模式、目标快照、提交和工作树状态、时间、版本和状态。
- 各模块结果和模块状态。
- Evidence ID、命令摘要、退出码、产物引用、哈希和清理结果。
- 生成测试元数据，包括生成原因、覆盖风险、文件路径、保留或清理结论。
- 修复轮次、原始失败、根因假设、最小 Diff 和 fresh rerun 记录。
- 同步变更记录、冲突检查结果和 Human Gate 记录。

上下文摘要、压缩提示、模型记忆或聊天消息不是任何 authority，也不能作为证据交付。

### 9.3 断点恢复

系统必须支持从最近检查点恢复。恢复时先读取宿主持有的运行注册表和运行目录，再检查当前项目快照是否变化：

- 未变化时，从未完成阶段继续。
- 发生变化时，重新盘点并只重新验证受影响模块和依赖链，必要时扩大范围。
- 无法证明旧证据仍适用时，旧证据只能保留为历史记录，不得继续支持当前 `PASS`。

### 9.4 报告交付

用户看到的输出由两部分组成：

1. 简明摘要，说明模式、目标快照、当前状态、重要发现、阻塞、人工事项、变更和测试的保留或清理结果。
2. 完整权威项目 QA 报告，包含范围、计划、执行证据、模块结果、发现、未验证项、Human Gates、剩余风险和结论门。

Main Agent 不得通过摘要重构完整报告。宿主必须直接交付已完成 Coordinator 结果中的完整报告 payload，并保留 raw parent message 与 delivered report 的哈希、字节数和匹配诊断。

报告只能输出必要的脱敏证据，不暴露原始 prompts、内部事件流、内部子会话原始输出、凭证、token、Cookie、个人数据或不必要的 secrets。报告不得输出发布批准。

## 11. 验收标准

### 11.1 产品验收

1. 用户输入“QA 整个项目”时，系统默认进入 `PROJECT_QA_ONLY`，能展示项目盘点、重要模块、风险计划和计划门。
2. 默认目标包含未提交变更，并在运行记录中显示快照身份、提交和工作树状态。
3. 用户明确请求修复并重跑时，系统进入 `PROJECT_FIX_AND_RERUN`；否则不修改产品文件，只允许写入已批准且被忽略的 QA 运行产物区域。
4. 至少三个真实公开仓库的已知 issue 修复前 / 修复后配对快照通过配对基准实验验证：Baseline 组与 Skill 组在相同快照、请求、模型、Agent 和预算下产出可比较证据，Skill 组在结论正确性、风险覆盖、命令相关性、可追溯性、BLOCKED/Human Gate 处理、只读合规、报告完整性和成本透明度等维度上优于 Baseline 组。配对快照至少覆盖两种技术栈。如果第三种技术栈因宿主本地工具不可用而无法完成，必须如实报告为未完成，不能计为 PASS。仅凭 manifest 声明、fixture 级验证或注入故障 fallback 不能支持真实项目效果声明。Java 的项目探测和计划生成可验证，但其真实项目门不阻塞 Phase 2 产品完成。
5. Coordinator 按 5.3 的规则输出重要模块、关键流程和 `Must Verify` 分类表，每项包含依据和来源；重要模块和关键流程均有当前执行证据，低风险遗漏、专项省略和残余风险可见。
6. 项目结果只能是 `PASS`、`FAIL`、`BLOCKED` 或 `NEEDS_HUMAN_REVIEW`，并符合本需求的状态规则。
7. 本地安全既有测试尽可能完整执行；外部、付费、凭证、生产、破坏性和依赖操作在批准前不执行。
8. 生成测试经过 Coordinator 设计、实施 Agent 写入和 QA Agent 独立验证，临时资产被清理，稳定回归测试只在修复模式保留。
9. 自动修复至多三轮，每轮保留原始失败和 fresh rerun evidence，三轮后仍失败时停止并报告。
10. 运行期间修改原始项目时，系统检测到冲突并停止同步，不覆盖用户变更。
11. 已被忽略的 `.qa/runs/<run-id>/` 或宿主持有的项目外等价目录中存在完整权威报告、manifest、模块结果、证据、测试元数据和变更记录，并能从检查点恢复；运行不得因此产生受跟踪的产品文件变更。
12. 最终输出包含简明摘要、完整报告、变更和测试的保留或清理说明、Human Gates、剩余风险，并明确不提供发布批准。
13. 同一项目存在可用上次运行时，系统自动标出新问题、已修复问题和持续问题，但只使用本次执行证据决定当前状态。
14. 实际证据、完整报告、run manifest、模块结果和 delivered payload 的哈希、状态与引用保持一致；任一无法解释的不一致都会阻止结论门和 `PASS`。
15. QA Coordinator 和 Module QA Agents 保持只读；测试生成、产品修复和同步只能由明确的宿主实施步骤完成，再交回独立 QA Agents 验证。

### 11.2 证据验收

每个 `Must Verify` 项必须具备验证 ID、实际命令或工具、观察结果、退出码或状态、产物引用、快照信息和状态。计划、命令意图、Agent 成功消息、历史报告或上下文摘要不能单独构成证据。

## 12. 测试策略

### 12.1 测试层次

1. **需求和结构契约测试**：检查模式名称、状态、边界规则、目录约定、必需报告字段和禁止声明。
2. **受控多模块 fixture 测试**：构造包含多个模块、共享依赖和关键流程的内部项目，预置已知 `PASS`、`FAIL`、`BLOCKED` 和 `NEEDS_HUMAN_REVIEW` 结果，验证项目级状态调和和证据追踪。fixture 项目是内部自动化测试输入，用于稳定验证状态、边界和恢复行为，不是面向用户展示的 demo 产品，也不代表真实项目覆盖或产品质量认证。
3. **流程行为测试**：验证项目盘点、计划门、模块分区、并发隔离、既有测试执行、专项风险选择和报告交付。
4. **生成测试测试**：验证测试用例设计、文件生成、QA 独立验证、稳定测试保留、临时资产清理，以及拒绝删除测试、跳过检查和弱化断言。
5. **自动修复测试**：验证原始失败保留、根因假设、最小 Diff、原始测试重跑、项目回归、fresh evidence 和三轮停止。修复生命周期仅在 fixture 和受控环境中验证；真实项目上修复保持禁用，直到 QA-only 配对基准门全部通过。
6. **隔离和冲突测试**：验证副本写入、原始项目不变、修复模式同步、原始项目变化检测和冲突停止。
7. **恢复和上下文测试**：在不同阶段中断运行，验证从 checkpoint 恢复；修改项目后验证受影响模块重新验证；验证 context summary 不能取代 manifest 或报告。
8. **来源和权限测试**：验证敏感命令、外部依赖、生产数据和破坏性操作进入 Human Gate，报告不泄露 secrets 和 raw internal data。
9. **Authority 和写入面测试**：验证报告、manifest、模块结果、实际证据和 delivered payload 的哈希及状态一致；验证 QA-only 只写入被忽略的 QA 产物区域或项目外存储，不产生受跟踪产品变更。
10. **分类规则测试**：验证核心入口、共享依赖、安全、数据、支付和项目启动模块被正确列为重要模块或 `Must Verify`，以及无法判断业务重要性时进入 Human Gate。
11. **命令策略测试**：验证 `APPROVED_DIRECT_LOCAL_CHECK`、`HUMAN_GATE_REQUIRED`、`BLOCKED_MISSING_PREREQUISITE` 和 `FORBIDDEN` 四种策略结果在各类命令上的正确判定和执行边界。

### 12.2 真实项目效果基准门

Phase 2 产品完成必须通过以下配对基准实验。实验使用真实公开仓库的已知 issue 修复前 / 修复后配对快照，在相同条件下比较 Baseline 组（不加载 Phase 2 Skill）与 Skill 组（加载当前版本 Phase 2 Skill pack）的 QA 产出。

**初始发布门（至少三对，至少两种技术栈）：**

| 配对 | 技术栈 | 修复前预期 | 修复后预期 | 说明 |
|---|---|---|---|---|
| 真实公开仓库 issue 配对 A | 技术栈 1 | `FAIL` | `PASS` | 修复前包含客观可复现缺陷，修复后缺陷已修正。 |
| 真实公开仓库 issue 配对 B | 技术栈 1 或 2 | `FAIL` | `PASS` | 同上。 |
| 真实公开仓库 issue 配对 C | 技术栈 2 | `FAIL` | `PASS` | 同上。 |

每对实验必须产出以下可独立审计的交付物：

- Baseline 组完整 QA 报告、执行证据和模块结果。
- Skill 组完整 QA 报告、执行证据和模块结果。
- 两组在八个效果维度上的逐项比较记录：客观结论正确性、风险与重要模块 / 关键流程覆盖、命令相关性与实际执行证据、可追溯性、BLOCKED 与 Human Gate 处理、只读合规、报告完整性、成本 / 时间透明度。

**配对快照要求**：

- 优先使用真实公开仓库的已知 issue 修复前 / 修复后配对快照。修复前快照的缺陷必须客观可复现，修复后快照的修正必须可验证。
- 如果真实 issue 配对不可得，可以使用人工注入故障的变体作为降级方案。注入故障的实验必须显式标注为 fallback，不能用于支持"真实项目效果"声明。
- 源项目零修改：所有配对快照的原始代码、测试、配置和文档在实验前后保持完全一致（哈希验证），仅 `.qa/` 运行产物区域或项目外存储被写入。

**技术栈覆盖**：

- 初始发布门至少覆盖两种技术栈。第三种技术栈因宿主本地工具不可用而无法完成时，必须如实报告为未完成，不能计为 PASS。
- 如果所有配对快照均来自同一技术栈，初始发布门视为未通过。
- Java 的项目探测、计划生成和 fixture 级验证在本阶段实现并通过自动化测试；Java 真实项目门不阻塞 Phase 2 产品完成。

**修复禁用**：修复在真实项目上保持禁用，直到 QA-only 配对基准门全部通过。修复生命周期正确性仅通过 fixture 和受控测试验证。

### 12.3 必测场景

| 场景 | 预期 |
|---|---|
| 多模块均有证据且关键预期满足 | 项目 `PASS`，低风险未验证项仍可见。 |
| 关键模块实际失败 | 项目 `FAIL`，保留失败证据和影响。 |
| 缺少关键验收数据或权限 | 项目 `BLOCKED`，记录精确重跑条件。 |
| 有证据但需要业务、UX、安全或设计决定 | 项目 `NEEDS_HUMAN_REVIEW`，记录 Human Gate。 |
| 生成测试存在无效断言 | 测试验证失败，不得作为产品 PASS 依据。 |
| 第三轮修复后仍失败 | 停止修复，保留三轮记录并报告。 |
| 原始项目在运行中改变 | 停止同步，报告冲突，不覆盖用户变化。 |
| 运行在模块执行中断开 | 从 checkpoint 恢复，重新验证必要范围。 |
| 项目历史报告显示旧问题已修复，但当前复现 | 当前证据决定 `FAIL`，历史只作比较上下文。 |
| 项目无 Web 或无统一测试框架 | 使用其可用的本地工具验证，不因技术栈不同而伪造状态。 |
| `.qa/` 未被忽略且不能安全建立本地排除 | 使用宿主持有的项目外运行目录，不修改受跟踪文件。 |
| 报告、manifest、模块结果或 delivered payload 不一致 | 结论门失败，不得输出项目 `PASS`。 |
| 关键共享依赖被错误标记为低风险 | 分类合同测试失败，要求补充依据或进入 Human Gate。 |
| 真实 issue 修复前配对快照，Baseline 组误判为 PASS | Skill 组应正确判定为 FAIL，效果维度记录 Baseline 误判。 |
| 真实 issue 修复后配对快照，Baseline 组误判为 FAIL | Skill 组应正确判定为 PASS，效果维度记录 Baseline 误判。 |
| 注入故障 fallback 实验 | 显式标注为 fallback，不用于支持真实项目效果声明。 |
| 第三种技术栈因宿主工具不可用而无法完成 | 如实报告为未完成，不能计为 PASS。 |

## 13. Definition of Done

Phase 2 v1 只有在以下条件全部满足时，才可提交阶段验收：

- 本文档中的已确认产品需求已由产品、工程和 QA 评审并形成实现任务。
- 两种用户模式、模式边界和默认行为均可被验证。
- 项目清单、快照、模块分区、计划门、结论门和四状态均已实现并有测试。
- 测试生成、独立验证、临时清理、稳定测试保留和三轮修复停止均有可复查证据。
- 隔离、副本同步和冲突停止经过自动化测试。
- 被忽略的 `.qa/runs/<run-id>/` 或宿主持有的项目外等价目录可保存权威报告并从 checkpoint 恢复，模型上下文摘要不承担 authority。
- 实际证据、报告语义、运行状态和交付 payload 的 authority 分工明确；不一致会失败关闭。
- QA Coordinator 和 Module QA Agents 保持只读，文件写入和修复由宿主实施步骤完成后再独立验证。
- 同一项目的连续运行能够自动比较新问题、已修复问题和持续问题，同时保持当前证据优先。
- 多模块 fixture 覆盖四种状态，且命令策略四种结果均有自动化测试覆盖。
- 证据最小化、脱敏、Human Gate、无证据不 PASS、fresh rerun 和无发布批准边界通过回归测试。
- 没有自动 Git commit、自动依赖安装、自动 release approval 或未确认的外部系统连接。

**仅 fixture 和契约测试不能完成 Phase 2。** 以下真实项目效果基准门是 Phase 2 产品完成的强制性前置条件：

- 至少三个真实公开仓库的已知 issue 修复前 / 修复后配对快照通过配对基准实验验证，至少覆盖两种技术栈。每对实验产出以下可独立审计的交付物：
  - Baseline 组完整 QA 报告、执行证据和模块结果。
  - Skill 组完整 QA 报告、执行证据和模块结果。
  - 两组在八个效果维度上的逐项比较记录：客观结论正确性、风险与重要模块 / 关键流程覆盖、命令相关性与实际执行证据、可追溯性、BLOCKED 与 Human Gate 处理、只读合规、报告完整性、成本 / 时间透明度。
- Skill 组在结论正确性、风险覆盖、命令相关性、可追溯性、BLOCKED/Human Gate 处理、只读合规、报告完整性和成本透明度等维度上整体优于 Baseline 组。
- 源项目零修改：所有配对快照的原始代码、测试、配置和文档在实验前后保持完全一致（哈希验证），仅 `.qa/` 运行产物区域或项目外存储被写入。
- 修复在真实项目上保持禁用，其生命周期正确性仅通过 fixture 和受控测试验证。
- 第三种技术栈因宿主本地工具不可用而无法完成时，如实报告为未完成，不能计为 PASS。
- Java 的项目探测、计划生成和 fixture 级验证已实现并通过自动化测试；Java 真实项目门不阻塞 Phase 2 产品完成。

**最终独立审查：**

- 由未参与实现的独立审查人对所有配对基准实验的 Baseline 组和 Skill 组完整报告、执行证据和模块结果进行逐项核对。
- 审查确认每对实验的 `PASS` 或 `FAIL` 判定与客观执行证据一致，不存在伪造、跳过或静默降级。
- 审查确认八个效果维度的逐项比较记录完整且可复现。
- 审查确认源项目零修改的哈希验证记录完整且可复现。
- 独立审查通过后，Phase 2 产品完成方可提交阶段验收。

## 14. 开源研究参考与设计原则

为设计运行状态和证据链，本阶段参考以下开源项目中可借鉴的模式：

- LangGraph 的 state 和 checkpoint 思路，强调可恢复的结构化运行状态。
- OpenHands 的 event stream 和 sub-conversation 思路，区分协调过程与可交付结果。
- SWE-agent 的 trajectory 思路，保留行动、观察和结果之间的过程关联。
- openQA 的 job 与 evidence provenance 思路，强调任务、证据来源和可审计关系。
- qa-use 的 run hierarchy 思路，按运行、阶段和子任务组织 QA 结果。

这些参考用于提炼状态持久化、运行层级、证据 provenance 和恢复原则，不代表 Phase 2 v1 必须采用任何一个框架。Phase 2 v1 优先在现有 Skill 和 OpenCode 架构中实现这些原则，待实际运行和技术评审后再决定是否引入外部框架或库。

## 15. 已确认需求与待技术设计事项

### 15.1 本次已确认的产品需求

- Phase 2 的核心对象是整个当前项目，而不是跨 Diff 报告聚合。
- 默认目标是显式选择的项目当前代码状态，包含未提交变更。
- 产品支持 `PROJECT_QA_ONLY` 和需明确请求的 `PROJECT_FIX_AND_RERUN`。
- 用户体验低摩擦，系统自动盘点、识别重要模块、设计计划并只询问真正的 Human Gate。
- 项目 PASS 要求重要模块和关键流程都有当前执行证据，低风险遗漏可见。
- 重要模块、关键流程和 `Must Verify` 使用明确分类规则，并为每项保留依据和来源。
- 四种 canonical status 保持为 `PASS`、`FAIL`、`BLOCKED`、`NEEDS_HUMAN_REVIEW`。
- 自动测试生成、独立测试验证、隔离、三轮修复限制、冲突停止、断点恢复和权威报告均为 v1 需求。
- QA Agents 保持只读；实施写入由宿主编排并在完成后交回 QA 验证。
- 不自动提交、不自动批准发布、不自动安装依赖，不把上下文摘要作为证据。
- Skill 保持技术中立，使用宿主和项目已有工具完成验证；不要求安装新的测试运行时，不要求为每种语言编写适配器。
- 效果通过配对基准实验验证：同一冻结快照、请求、模型、Agent 和预算下，Baseline 组（不加载 Skill）与 Skill 组（加载当前版本 Phase 2 pack）产出可比较证据。
- 八个效果维度：客观结论正确性、风险与重要模块 / 关键流程覆盖、命令相关性与实际执行证据、可追溯性、BLOCKED 与 Human Gate 处理、只读合规、报告完整性、成本 / 时间透明度。
- 优先使用真实公开仓库的已知 issue 修复前 / 修复后配对快照；注入故障 fallback 必须显式标注，不能支持真实项目效果声明。
- 初始发布门：至少三对真实 issue 配对快照，至少覆盖两种技术栈；第三种技术栈因宿主工具不可用而无法完成时如实报告为未完成，不能计为 PASS。
- 修复在真实项目上保持禁用，直到 QA-only 配对基准门全部通过；修复生命周期仅在 fixture 和受控测试中验证。
- 仅 fixture 和契约测试不能完成 Phase 2；真实项目效果基准门是产品完成的强制性前置条件。
- 源项目零修改：所有配对快照的原始代码在实验前后哈希一致。
- M1-M7 安全约束（不自动安装、不网络出站、不使用凭证、不访问生产、不写回受跟踪文件、不自动 commit/push、不自动批准发布）在基准实验中与生产使用中同等生效，不作为独立策略引擎或运行时的产品功能对外交付。
- 最终独立审查：由未参与实现的独立审查人对所有配对基准实验的 Baseline 组和 Skill 组完整报告、执行证据和模块结果进行逐项核对，确认判定一致、哈希一致、源项目零修改。

### 15.2 留给技术设计的事项

以下事项尚未在本需求基线中指定具体实现，必须在技术设计阶段单独评审：

- run manifest 的精确 JSON schema、版本策略和迁移策略。
- 日志、截图、视频、临时测试和报告的具体保留时长与容量数字。
- 文件复制、快照、容器、工作树或其他隔离实现方式。
- 模块 Agent 的最大并发数、共享资源调度和超时策略。
- 技术栈探测、测试命令发现和框架适配的具体实现。

技术设计不得反向改变本节 15.1 的产品约束。若实现方案无法满足证据优先、Human Gate、隔离、当前证据判定和无自动发布批准等约束，应回到需求评审，而不是静默降低边界。
