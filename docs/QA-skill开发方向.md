# QA Skill 开发方向

## 文档定位

本文档是 QA Skill 当前的权威方向，用于产品、工程、QA 和需求方对齐。旧文档 `qa-workflow-skill-research-and-dev-plan.md` 与 `qa-skill-mvp-requirements.md` 仍可作为参考，但发生冲突时以本文档为准。

QA Skill 不是测试框架、工具集合或自动发布系统，而是一套可复用的质量验证方法。它先建立可信的标准流程，再逐步适配项目上下文和项目知识。

## 两项核心能力

### 1. 可复用的标准质量验证流程

面向没有完整 QA 方法的团队，提供从明确目标到人工决策的闭环：澄清范围与非目标，识别风险，设计并执行验证，保留可复查证据，暴露未知项和剩余风险，并把验收与发布决定交给人。

### 2. 渐进式项目适配与执行提效

主动获取与当前目标相关的项目管理上下文，例如 GitHub Issue、PR、Jira、Linear、需求、事故和讨论，再通过与人的交互及人工治理积累可复用的项目知识，改善范围判断、风险识别和验证设计。

能力 1 是基础，能力 2 是适配层。项目适配可以改变验证内容、优先级和执行方式，但不能改变核心证据规则和人工决策规则。提效的目标是减少遗漏和重复判断，不是追求自动化数量。

## 一套共享 QA 工作流

所有阶段复用同一条闭环，范围可以从一次 Diff 扩大到项目或发布：

```text
用户手动触发，主 Agent 交接 supplied skill source path、resolved skill source path、supplied product target path、resolved product target path、目标范围和非目标、用户上下文及已知约束
→ 同一 QA subagent 先执行 Repository Preflight，确认显式 product target、仓库边界、目标范围和可用 Diff；歧义、缺失或不可读时 BLOCKED
→ 独立读取或检查实际目标变更或可用 Diff，不依赖摘要
→ 记录 Change Intake，分离 `Observed Facts`、带置信度和依据的 `Inferred Intent`、带来源/负责人的 `Authoritative Acceptance Criteria`、`Unresolved Questions`
→ 定义范围与非目标
→ 分析风险
→ 按风险设计和选择验证层
→ 按风险执行只读验证并收集证据
→ 分类发现
→ 外部修复或其他实质变化后，使用 fresh rerun evidence 重跑
→ 暴露未知项与剩余风险
→ 交给人做验收和发布决定
```

验证层按风险选择，不是固定套餐：

| 验证层 | 主要关注 |
|---|---|
| 静态与单元 | 代码、配置、规则和局部逻辑 |
| API 与集成 | 契约、服务协作、数据流和权限 |
| E2E 与系统 | 完整链路、用户路径和系统可见行为 |
| 专项非功能 | 性能、安全、兼容性、可靠性、可访问性等 |
| 人工验收 | 业务意图、主观体验、歧义需求和接受条件 |

各层是否执行由风险决定，省略或阻塞的理由必须可见。低层 PASS 不代表所需高层或用户可见行为已被证明。

## 四阶段路线

### Phase 1：从单个 Diff 建立稳定的 QA 工作流

**价值与目标**：让团队能围绕一次功能、修复或变更，完成范围清楚、风险可解释、证据可复查的 Diff QA。

**操作闭环**：主 Agent 交接 supplied/resolved skill source path、supplied/resolved product target path、目标和上下文，QA subagent 先执行 Repository Preflight，要求显式 target，不从 skill source 或 cwd 推断目标；歧义、缺失或不可读时澄清或 BLOCKED；ancestor repo 不自动成为 untracked/no-history target 的有效基线；没有可用 Diff 时只阻塞 Diff-dependent checks。Phase 1 的 Repository Preflight 仅保持紧凑的行为级契约，详细 Git 命令配方，例如 literal pathspec、fsmonitor、OID 和 worktree topology，属于后续增强，不是当前最小契约的隐含要求。随后再独立检查实际 Diff，然后记录 Change Intake 并分离 `Observed Facts`、`Inferred Intent`、`Authoritative Acceptance Criteria` 和 `Unresolved Questions`；之后才定义范围、分析风险，按风险选择验证层，检查已有测试覆盖和可用命令；以只读方式执行验证并收集证据，区分产品问题、测试问题、环境问题和需求问题，产品或测试修复在 QA 之外完成，外部修复后使用 fresh rerun evidence 重跑，最后生成可供复核的证据报告并保留人工决定。pack self-tests 和 discovery checks 只是 skill pack 完整性证据，不能替代 product-target QA。

**边界与非目标**：QA 是只读的，不编辑产品源代码、产品测试或测试文件、fixtures、snapshots、配置或文档；只允许写入 QA 报告和获准的临时 QA 产物，例如证据日志或截图。验证若需要项目文件编辑，必须停止并记录问题。不得绕过人工判断或自动批准发布，不自动修复产品；产品或测试修复在 QA 之外完成，外部修复或其他实质变化后必须有 fresh rerun evidence 才能改变状态。

### Phase 2：将同一工作流扩展到项目、子系统或发布级 QA

**价值与目标**：汇总并扩展 Diff QA，形成项目、子系统或发布级的风险与覆盖矩阵，发现跨模块风险、覆盖缺口和剩余风险，并把项目 QA 基线反馈给后续 Diff QA。

**操作闭环**：明确整体范围和非目标，聚合已有变更证据，分析跨模块和共享依赖风险，按风险补充验证，执行或重跑必要验证，汇总证据、缺口、阻塞和剩余风险，提交人工复核。

**边界与非目标**：不宣称穷尽覆盖或完整质量认证，不用覆盖率、通过数量或单一分数替代风险判断，不自动替代 QA、验收人或发布负责人。

### Phase 3：主动获取相关项目上下文

**价值与目标**：从当前且相关的项目记录中补足背景，减少需求分散、历史缺失和风险线索遗漏，提高范围和验证设计的准确性。

**操作闭环**：只检索相关的当前或历史 Issue、PR、需求、事故、讨论和约束，检查来源、时效性、相关性及冲突；将可靠上下文用于调整范围、风险和验证设计，再执行 Phase 1 或 Phase 2，并保留上下文边界和实际执行证据。

**边界与非目标**：上下文不是证据。项目记录不能自动产生 PASS，也不能自动移除验证项，更不能直接成为持久规则。与当前需求、实际行为或执行证据冲突时，必须保留冲突并交给人判断。

### Phase 4：通过与人的交互及人工治理积累可复用项目知识

**价值与目标**：把反复验证、经确认且有边界的项目经验沉淀下来，减少重复理解，同时保持知识可追溯、可修正和可撤销。

**操作闭环**：当前证据可以形成知识候选；由人审查并批准其来源、范围、版本、适用条件和限制；批准后的知识可被复用、纠正或撤销，并始终重新对照当前需求、风险和执行证据。

**边界与非目标**：知识必须受人治理。目前先拒绝不受控自我学习、静默改变政策、未经批准自动生效，以及让历史知识覆盖当前需求或证据。知识只能辅助判断，不能代替当前验证和人工决策。

## 统一护栏

- 没有实际证据，不得标记 PASS。
- 未知、阻塞、跳过、未验证和剩余风险必须显式可见。
- 不得静默扩大范围，外部记录只能作为上下文，不能作为证明。
- 当前需求和当前证据优先于历史记录与项目知识。
- 歧义需求、主观体验、业务接受和发布决定由人负责。
- QA 默认只读，不得编辑任何项目文件；只能写入 QA 报告和获准的临时 QA 产物。产品或测试修复必须在 QA 之外完成，修复或其他实质变化后必须提供 fresh rerun evidence。
- CI/CD 只是可选的触发、执行和证据通道，不是核心能力，也不是发布授权者。

## 需求方对齐结论

请对齐以下方向：

1. QA Skill 先提供可复用的标准质量验证流程，再提供渐进式项目适配与治理型知识复用。
2. 发展顺序固定为：单个 Diff、项目级 QA、主动获取项目上下文、通过与人的交互及人工治理积累知识。
3. 无证据不通过，未知与剩余风险不隐藏，外部记录不等于证据，验收与发布始终由人负责。

成功标准是更好地识别风险、设计验证、保留证据和支持决策，而不是增加自动化数量，更不是承诺全自动 QA、穷尽认证或自动放行。
